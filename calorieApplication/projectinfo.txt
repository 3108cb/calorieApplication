Project Brief: Simple Manual Calorie Tracker (iOS)

Project Name: Calorie & Macro Log
Target Platform: iOS (Native/SwiftUI preferred for modern iOS development)
Focus: Minimalist, manual input, local data tracking.

I. Core Application Goals & Focus

The primary goal of this application is to provide a clean, fast, and highly manual way for users to track their daily intake of Calories, Protein, and Fat.

Primary Metrics: Calories, Protein (g), and Fat (g).

Secondary Metric: Weight (kg/lb).

Target User: Users who prefer manually entering totals rather than relying on large food databases or integrations.

II. Design & User Experience (UX)

A. Aesthetic Requirements

Design Style: Minimalist, clean, and highly functional.

Color Scheme: Dark Mode is the preferred aesthetic. Use high-contrast elements and limited, purposeful color for emphasis (e.g., green for positive progress, red/orange for over-limit).

Typography: Clear, legible, and simple system fonts (like San Francisco).

B. Navigation & Screens (3 Total)

Navigation must use a simple, persistent Tab Bar at the bottom of the screen to switch between the three main views.

Screen 1: Dashboard (Main Screen)

Purpose: The default view for daily tracking and quick logging.

Key Data Display:

User's Daily Calorie Target (must be set in a separate settings area, initially).

Calories Remaining Today (Calculated: Target - Consumed).

Current progress for Protein (Consumed/Target) and Fat (Consumed/Target).

Primary Action: A highly visible, dedicated "Add Meal" Button placed immediately below the main calorie display for rapid data entry.

Screen 2: Calorie History

Purpose: Viewing past consumption trends.

Display: A calendar view or simple list/chart showing the total calories consumed for each day within the current calendar month.

Historical Access: The user must be able to view logs dating back up to the past year.

Screen 3: Weight Tracker

Purpose: Simple logging and visualization of weight history.

Functionality: Allow the user to input their current weight and date, and display a historical log or simple chart of previous weight entries.

III. Data Flow & Functional Requirements

A. Data Input

The application is purely manual input. When the user clicks the "Add Meal" button:

They should be prompted to input:

Meal Category: (Dropdown/Selector: Breakfast, Lunch, Dinner, Snack).

Calories (kcal): (Number Input).

Protein (g): (Number Input).

Fat (g): (Number Input).

Input should immediately update the daily totals on the Dashboard.

B. Data Persistence & Deletion

Storage: All data must be saved using local storage only (no external accounts or APIs required).

Intra-Day Deletion:

The user must be able to see the list of individual Meal Objects logged for the current day only.

The user must be able to delete individual Meal Objects for the current day, which immediately updates the daily totals.

End-of-Day Archiving (CRITICAL):

At midnight (or on the first log of a new day), the app must archive the day's total consumption.

Only the total daily consumption figures are saved:

Date

Total Calories Consumed

Total Protein Consumed

Total Fat Consumed

The individual Meal Objects (Breakfast, Lunch, etc., with their associated names/values) are permanently discarded/cleared.

C. Scope Exclusions (Must Not Implement)

No external API or food database lookups.

No HealthKit or any other third-party integration.

No user authentication or cloud syncing.

No water tracking, step counting, or other secondary metrics beyond the core three (Calories, Protein, Fat) and Weight.

IV. Implementation Summary (How the App Was Assembled)

This section explains how the brief was implemented in the Xcode project and which files contain which responsibilities.

A. Data Models and Storage

1. Models.swift

- Defined the core data structures as Swift types:
  - MealCategory: An enum (Breakfast, Lunch, Dinner, Snack) used as a selector when logging meals.
  - Meal: Represents a single logged meal with id, date, category, calories, protein, and fat.
  - DaySummary: Represents one archived day with total calories, protein, and fat for that date.
  - WeightEntry: Represents one recorded body weight value with a date and weight.
- All models conform to Codable and Identifiable so they can be:
  - Encoded/decoded to and from local storage.
  - Used easily in SwiftUI ForEach lists.

2. CalorieDataStore.swift

- Implemented CalorieDataStore as an ObservableObject, which is the central source of truth for:
  - todaysMeals: the list of Meal objects for the current day only.
  - daySummaries: the list of archived DaySummary records (used for history).
  - weightEntries: the list of WeightEntry records (for the weight tracker).
  - dailyCalorieTarget, dailyProteinTarget, dailyFatTarget: user-configurable daily targets.
- All state is persisted using UserDefaults (local storage only) via JSONEncoder/JSONDecoder:
  - Todays meals, day summaries, and weight entries are encoded to Data and stored under keys.
  - Daily targets are stored as Int values under dedicated keys.
- On initialization, the store:
  - Loads any previously saved data from UserDefaults.
  - Handles the "day rollover" logic to decide whether to archive yesterday’s data.
- Day rollover / end-of-day archiving logic:
  - The store tracks a lastActiveDate value in UserDefaults.
  - When the app starts or when we add a meal, it checks whether lastActiveDate is still the same calendar day as "now".
  - If the day has changed, it:
    - Sums the current todaysMeals into totals for calories, protein, and fat.
    - Creates a DaySummary for lastActiveDate with those totals.
    - Appends that DaySummary to daySummaries.
    - Clears todaysMeals so the new day starts empty.
    - Updates lastActiveDate to the new date.
- Intra-day deletion:
  - Exposes deleteMeal(_:) that removes a specific Meal from todaysMeals and re-saves.
- Weight logging:
  - Exposes addWeightEntry(weight:date:) to create WeightEntry objects, store them, and keep them sorted by date.
- Daily targets (settings):
  - Exposes updateDailyTargets(calories:protein:fat:) to update the three daily target values and persist them.
- Computed values:
  - todayTotalCalories, todayTotalProtein, todayTotalFat: simple sums of todaysMeals.
  - caloriesRemainingToday: dailyCalorieTarget minus todayTotalCalories, clamped at zero.
  - recentSummaries: filters daySummaries to only the last 365 days and sorts them by descending date for the history screen.

B. UI Layers and Screens (SwiftUI)

1. Views.swift – ContentView and Tab Bar

- ContentView is the SwiftUI entry point for the UI:
  - Creates a single @StateObject CalorieDataStore instance.
  - Wraps the core screens in a TabView with three tabs:
    - DashboardView (Today)
    - HistoryView (Calorie History)
    - WeightTrackerView (Weight)
  - Applies a dark appearance and green accent for the minimalist dark mode UI.

2. DashboardView (Today screen)

- Uses @EnvironmentObject CalorieDataStore to read/write shared state.
- Main elements:
  - Main summary card:
    - Shows "Calories Remaining", the remaining calories value, and a line for "Target X • Consumed Y".
  - Macro progress card:
    - Shows progress bars for Protein and Fat, using consumed vs. target values from the store.
  - Today's meals list:
    - Displays a list of all todaysMeals with category and macro details.
    - Allows swipe-to-delete on individual meals; deletion updates totals immediately.
- Actions:
  - "Add Meal":
    - A button in the navigation bar and above the meal list that triggers a sheet showing AddMealView.
  - "Targets / Settings":
    - A gear icon in the navigation bar that opens TargetsSettingsView in a sheet for editing daily targets.

3. AddMealView (manual meal logging)

- Presented as a sheet from DashboardView.
- Uses:
  - A Picker for MealCategory (Breakfast, Lunch, Dinner, Snack).
  - Text fields for Calories, Protein, and Fat (numberPad keyboard).
- Save behavior:
  - Validates that all three numeric fields can be converted to Int.
  - Calls store.addMeal(category:calories:protein:fat:) to:
    - Append a new Meal to todaysMeals.
    - Update totals and persist state.
  - Dismisses itself after a successful save.

4. HistoryView (calorie history)

- Shows a NavigationView containing a List.
- If there is no history:
  - Displays a short explanatory message about how days are archived automatically.
- If there is history:
  - Iterates over store.recentSummaries (up to one year of data).
  - For each DaySummary, shows:
    - The date.
    - The total calories in green.
    - The total protein and fat in a smaller gray line.
- This implements the "Daily Totals Only" history requirement using the archived day summaries.

5. WeightTrackerView (weight logging)

- Simple, minimal design for logging and viewing weights:
  - A text field for entering the current weight (decimalPad).
  - A "Log" button that:
    - Validates the text as a Double.
    - Calls store.addWeightEntry(weight:) to create and persist a WeightEntry.
  - A list of past weightEntries, newest first, showing:
    - The entry date.
    - The weight value in green.

6. TargetsSettingsView (daily target settings)

- Presented as a sheet from DashboardView when tapping the gear icon.
- On appear:
  - Pre-fills text fields with the current dailyCalorieTarget, dailyProteinTarget, dailyFatTarget from the store.
- Save behavior:
  - Ensures all three fields are valid Int values.
  - Calls store.updateDailyTargets(calories:protein:fat:) to update and persist targets.
  - Dismisses the sheet.
- These targets are then used by:
  - The Dashboard summary ("Target X").
  - The macro progress bars for Protein and Fat.

C. App Entry and Integration

1. SceneDelegate.swift

- The project uses the UIKit app lifecycle with SceneDelegate.
- Modified scene(_:willConnectTo:options:) to:
  - Create a UIWindow with the incoming UIWindowScene.
  - Set the rootViewController to a UIHostingController(rootView: ContentView()).
  - Call makeKeyAndVisible() so the SwiftUI UI becomes the visible app UI.
- This effectively replaces the storyboard-based ViewController with the SwiftUI-based tabbed interface defined in ContentView.

2. AppDelegate.swift

- Left mostly unchanged, using the default template behavior.
- It coordinates scene sessions, while the actual UI is managed by SceneDelegate and SwiftUI.

D. How Requirements Map to the Implementation

- Manual input only:
  - All logging (meals and weight) uses text fields and pickers; there are no external APIs or databases.
- Local storage only:
  - Data is persisted via UserDefaults in CalorieDataStore; no network or cloud code exists.
- Daily totals and archiving:
  - todaysMeals holds only the current day’s meals.
  - At day change, those meals are summarized into DaySummary objects and cleared.
- Intra-day deletion:
  - The Dashboard’s meal list supports swipe-to-delete, which calls store.deleteMeal(_:) and updates totals immediately.
- History up to one year:
  - recentSummaries in the store filters archived DaySummary records to the last 365 days, which HistoryView displays.
- Minimalist dark mode UI:
  - ContentView enforces a dark color scheme and uses a limited accent color (green) for positive progress and emphasis.
